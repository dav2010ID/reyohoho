# Облачная история (подготовленная версия, ещё не включена)

## Что меняется

- Опциональное хранение истории в D1 через существующий Worker `api.reyhoho.fun`.
- Существующий вход через Telegram сохраняется. Firebase здесь используется для Remote Config, НЕ для авторизации.
- Только история текущего аккаунта переключается на D1. Остальные списки продолжают использовать прежний backend.
- Включение требует явного согласия на импорт локальной истории. По умолчанию функция выключена.
- Гостевая история остаётся локальной. Выход/смена токена отключает облачную историю.
- Новые просмотры и удаления отправляются при соответствующем действии; история загружается при открытии главной страницы или кнопкой в настройках.
- Это НЕ фоновая offline-очередь и НЕ синхронизация позиции видео. При неудачной отправке локальная запись остаётся; её можно добавить кнопкой «Добавить локальную историю в облако».
- Импорт объединяет записи, но не перезаписывает существующие и не восстанавливает удалённые.
- GET/экспорт/импорт ограничены 1000 фильмами, серверный импорт — пакетами по 40. Данные имеют фиксированный список полей.
- Сервер ограничивает аккаунт 5000 уникальными ID, включая tombstones. Счётчик изменяется SQL-триггерами в той же транзакции, без полных сканирований при импорте.
- При удалении стираются название, постер, дата и остальные метаданные. ID и признак удаления сохраняются, чтобы импорт со старого устройства не восстановил запись. Для полного стирания аккаунта администратор должен удалить строки `user_history` и `history_quota` по серверному `user_id`; после этого старый импорт сможет восстановить фильмы.
- При отключении синхронизации облачные данные НЕ удаляются.

## Включение в Cloudflare

Ничего из нижеописанного автоматически не создано и не опубликовано.

1. Создать D1 через Cloudflare Dashboard → Workers & Pages → D1, например с именем `reyohoho-history`.
2. Добавить в `workers/kinobox-search/wrangler.jsonc` реальный binding из Cloudflare (не выдумывать ID):

```jsonc
"d1_databases": [{
  "binding": "HISTORY_DB",
  "database_name": "reyohoho-history",
  "database_id": "<реальный ID созданной базы>",
  "migrations_dir": "migrations"
}],
"vars": {
  "HISTORY_AUTH_USER_URL": "https://<доверенный backend>/user"
}
```

3. `HISTORY_AUTH_USER_URL` — фиксированный HTTPS `/user` того backend, который реально выдаёт ваши Telegram access_token. Он должен возвращать 401/403 для неверного токена и JSON `{ "id": ... }` для действительного. Проверить это вручную ДО включения функции. URL никогда не берётся из клиентского запроса; редиректы запрещены. Если сервер возвращает иную структуру, адаптировать её только после проверки.
4. Применить миграцию `workers/kinobox-search/migrations/0001_history.sql` к D1 (Dashboard SQL console либо Wrangler D1 migrations).
5. Опубликовать Worker обычным процессом проекта, сохранив custom domain и запрет workers.dev. Текущую рабочую Kinobox HTTP/2 реализацию не менять.
6. Проверить 401 без токена, разные аккаунты, операции PUT/GET/DELETE, повторный импорт после удаления. История никогда не должна попадать в общий cache.
7. До публичного включения настроить ограничение частоты для `/api/history*` (Cloudflare rate limiting/WAF по доступному тарифу), мониторинг D1 и backend `/user`. CORS не заменяет авторизацию и не защищает от расходов на массовые запросы. Не включать логирование токенов, тела или названий фильмов.
8. Только после успешных проверок собрать frontend с `VITE_CLOUD_HISTORY_ENABLED=true`. Без этого значения облачные запросы не выполняются; инструменты локального переноса доступны.

Настройки → Поведение → «Облачная история и перенос».
В случае отказа D1 пользователь видит ошибку, локальное содержимое не очищается. На новом устройстве облако нужно включить явно. Не импортировать локальные записи другого человека в свой аккаунт.

## Перенос с GitHub Pages на новый домен

Правильный старый origin: `https://dav2010id.github.io` (НЕ `dav2010.id.github.io`).

localStorage разделён по origin, а не по пути. Новый домен не может напрямую прочитать старую историю. Старый репозиторий `/reyohoho/` теперь перенаправляет на custom domain, поэтому разместить там bridge недостаточно.

### Подготовить отдельную страницу на старом origin

1. В аккаунте **dav2010id** создать отдельный публичный репозиторий **reyohoho-history-transfer**.
2. Скопировать четыре файла из `migration/history-transfer/` в корень этого репозитория: `index.html`, `transfer.js`, `history-data.js`, `style.css`.
3. Включить GitHub Pages из ветки, корень `/`. **Custom domain не указывать, CNAME не добавлять.**
4. Проверить, что страница открывается именно по `https://dav2010id.github.io/reyohoho-history-transfer/` без редиректа на reyhoho.fun. Если у пользовательского сайта `dav2010id.github.io` тоже настроен custom domain, сначала понадобится отдельное решение для сохранения старого origin.
5. Не добавлять аналитику, сторонние скрипты и токены. Эта страница имеет доступ к прежнему localStorage.

### Для пользователя

Открыть новый сайт в **том же браузере и профиле**, где использовался старый:

1. Настройки → Поведение → «Перенести со старого сайта».
2. Разрешить popup; он покажет количество записей.
3. Нажать «Перенести на reyhoho.fun».
4. На новом сайте подтвердить импорт. Уже имеющиеся записи не удаляются.
5. Если включена облачная история, импорт попадёт в свой аккаунт D1. Если вы вошли, но D1 не включена — в историю аккаунта на прежнем backend (существующие записи не перезаписываются). Для гостя — только в локальную историю нового домена.

Перенос не запускается без клика и подтверждения. Принимающая страница проверяет точный origin, окно-отправитель и случайный одноразовый nonce. История не передаётся в URL, токены/настройки не читаются. Исходные данные не удаляются.

### Запасной вариант JSON

Открыть bridge напрямую в старом браузере → «Скачать JSON». На новом сайте выбрать «Импорт JSON», затем подтвердить импорт. Можно перенести файл между устройствами самостоятельно.

Очищенную браузером историю восстановить нельзя. Incognito и другой профиль не имеют доступа к прежним данным.

## Проверки

- `npx vitest run`: реальный SQLite через Node `node:sqlite`, изоляция аккаунтов, удаление/повторный импорт, CORS, отказы авторизации, лимиты, нормализация legacy и защита postMessage.
- `npm run lint`, `npm run build:github`, `npm run check:encoding`.
- Проверить UI в браузере и реальную D1 после конфигурации. SQLite unit-тесты не являются проверкой deployed D1/backend.

Документация Cloudflare: D1 prepared statements, D1 database batch и D1 get started (developers.cloudflare.com).
