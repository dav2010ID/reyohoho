### Архитектура в двух абзацах

Vue 3 + Pinia + ViteSSG, PWA, деплой на GitHub Pages за Cloudflare. Данные идут тремя путями:
(1) публичный каталог — Cloudflare Worker `api.reyhoho.fun` (Kinopoisk GraphQL → fallback Kinobox через
собственный TLS/HTTP2-клиент, Cache API, rate limiters); (2) аккаунт — тот же Worker + D1 (Telegram-вход,
opaque-сессии `rh1_…`, списки, облачная история); (3) «социальные» функции (комментарии, оценки, заметки,
тайминги, аниме, поиск по IMDb/Shikimori) — старый Sanic-backend по `VITE_APP_API_URL`. Плееры ищутся
в браузере цепочкой DDBB Live → DDBB → Kinobox.

Сильные стороны, которые стоит сохранить: аккуратное разбиение бандла и ленивые чанки; защита от
устаревших ответов (`latestRequest`, проверки токена после каждого `await`); Worker с хэшированными
токенами, атомарным подтверждением входа и fail-closed лимитерами; DOMPurify для HTML; 651 тест.

Главная системная проблема: фронтенд собран для трёх backend-ов одновременно, но в продакшене
настроен только Worker. Отсюда «мёртвые» элементы интерфейса (H2) и большая часть сложности `src/api`.

## 1. Critical

### C1. Поиск плееров: до 45 секунд ожидания и «Плееры не найдены» — Баг (вживую)

- **Где:** `src/api/movies.js:17` (`PLAYER_PROVIDER_TIMEOUT_MS = 15000`), `:144-202`
  (`getPlayersWithFallback`), `src/api/contentProviderOrder.js:20-33`,
  `workers/kinobox-search/kinobox-content.mjs:53-59, 93`, `src/components/PlayerComponent.vue:54-60`.
- **Проблема:** провайдеры опрашиваются строго по очереди, у каждого таймаут 15 с. На проверке
  09.11 страница `/movie/301` ~30 с показывала спиннер и закончила сообщением «Плееры не найдены»:
  `ddbb_live` — таймаут 15 с, `ddbb` — Network Error, `kinobox` — таймаут 15 с (консоль браузера;
  `curl` к Worker вернул 504 ровно через 15.19 с). В пустом состоянии нет кнопки «Повторить»,
  переключатель плееров показывает «Загрузка плееров…», хотя подсказка советует «сменить плеер выше».
- **Причина:** (1) последовательный fallback без параллельного старта; (2) нет памяти о сбоях —
  следующий фильм снова ждёт те же 15 с на мёртвом провайдере; (3) клиентский таймаут равен дедлайну
  Worker (15 с, а с ожиданием lease до +10 с), поэтому браузер рвёт запрос раньше, чем получит
  `504`/`Retry-After`; (4) запросы не отменяются при уходе со страницы (см. M3).
- **Решение:** «хеджированный» запуск — следующий провайдер стартует через 2–3 с или сразу после
  ошибки предыдущего, побеждает первый непустой ответ; короткая память о сбоях; дедлайн Worker
  меньше клиентского.

  ```js
  // src/api/movies.js — эскиз
  const HEDGE_DELAY_MS = 2500
  const COOLDOWN_MS = 5 * 60_000
  const failedAt = new Map() // provider -> timestamp, только на сессию

  const getPlayersWithFallback = (contentId, playerOptions = {}) => {
    const all = getPlayerProviderOrder(getCurrentProvider())
    const healthy = all.filter((p) => Date.now() - (failedAt.get(p) || 0) > COOLDOWN_MS)
    const order = healthy.length ? healthy : all
    const abortAll = new AbortController()
    playerOptions.signal?.addEventListener('abort', () => abortAll.abort(), { once: true })

    return new Promise((resolve, reject) => {
      let next = 0, running = 0, timer = null
      const finish = (players) => { clearTimeout(timer); abortAll.abort(); resolve(players) }
      const settle = (provider, failed) => {
        if (abortAll.signal.aborted) return // уже есть победитель
        if (failed) failedAt.set(provider, Date.now()) // пустой ответ сбоем не считается
        running--
        if (next < order.length) launch()
        else if (running === 0) resolve({})
      }
      const launch = () => {
        clearTimeout(timer)
        if (next >= order.length) return
        const provider = order[next++]
        running++
        // attemptProvider — текущее тело цикла: withProviderTimeout + аналитика попытки
        attemptProvider(provider, contentId, { ...playerOptions, signal: abortAll.signal }).then(
          (players) => (hasPlayers(players) ? finish(players) : settle(provider, false)),
          (error) => (playerOptions.signal?.aborted ? reject(error) : settle(provider, true))
        )
        if (next < order.length) timer = setTimeout(launch, HEDGE_DELAY_MS)
      }
      launch()
    })
  }
  ```

  Дополнительно: `PLAYER_PROVIDER_TIMEOUT_MS` 15 → 8–10 с; дедлайн в Worker
  (`kinobox-content.mjs:93`) 15 → 10–12 с, чтобы клиент успевал получить 504; в пустом состоянии —
  кнопки «Повторить» и «Сменить источник» (ведёт в Настройки → Источники); в спиннере показывать,
  какой источник опрашивается.
- **Эффект:** худший случай 45 с → ~10–12 с; при одном живом провайдере результат за 2.5 с + его
  отклик вместо 15–30 с; повторные открытия не ждут мёртвый источник.
- **Сложность:** 4–6 ч с тестами (`movies.player-fallback.spec.js` уже покрывает порядок). Риск:
  больше одновременных запросов к провайдерам (до 3 на открытие) и изменение смысла аналитики
  `fallback_used` — события нужно пересмотреть.

## 2. High

### H1. `/auth-success?token=…` подменяет сессию по ссылке — Баг (вживую)

- **Где:** `src/components/AuthSuccess.vue:68-73`.
- **Проблема:** токен из query-строки принимается безусловно и перезаписывает текущую сессию.
  Проверено на проде: переход на `/auth-success?token=<произвольная строка>` записал её в
  `localStorage.auth`, после чего главная постоянно показывает «Ошибка: Дождитесь подтверждения
  аккаунта» (в меню при этом «Войти», кнопки выхода нет). С валидным `rh1_`-токеном атакующего это
  session fixation: жертва оказывается в чужом аккаунте, её дальнейшая история просмотров пишется туда,
  а для legacy-токенов локальная история и списки выгружаются без подтверждения (ветка `else`, `:155+`).
- **Причина:** наследие схемы «JWT в URL». Текущий вход (`Login.vue:131`) кладёт токен в store и
  делает `router.replace('/auth-success')` без параметров; ни фронтенд, ни backend, ни Worker такую
  ссылку больше не формируют.
- **Решение:**

  ```js
  // AuthSuccess.vue
  if (new URLSearchParams(window.location.search).has('token'))
    window.history.replaceState({}, document.title, `${base.value}auth-success`)
  const token = authStore.token // токен из URL не принимается
  if (!token) throw new Error('Не удалось подтвердить вход. Войдите через Telegram ещё раз.')
  ```

  и в `catch` внешнего `try`: при `401` или неподходящем формате токена вызывать `authStore.logout()`,
  чтобы не оставалась «полусессия» (`token` есть, `user` нет).
- **Эффект:** закрыты подмена аккаунта и принудительный выход по ссылке; исчезает неустранимое
  состояние ошибки.
- **Сложность:** ~1 ч + правка `AuthSuccess.spec.js`. Риск: если десктоп-клиент или расширение
  всё ещё открывают `/auth-success?token=` — сначала проверить их код.

### H2. В продакшене не настроен основной backend: часть интерфейса заведомо не работает — Баг (вживую)

- **Где:** `.env` (`VITE_APP_API_URL=` пусто, файл в git), `.github/workflows/github.yaml` (переменная

  - комментарии — блок пишет «Комментариев пока нет», после раскрытия «Не удалось загрузить
    комментарии. Повторить» (повтор всегда неуспешен);
  - заметки, тайминги и «Родительский гид», страницы `/shiki/:id`, поиск по «ID Shikimori» и «ID IMDB»

- **Причина:** нет единого признака «legacy-backend доступен»; `accountCapabilities` учитывает только

- **Эффект:** пользователь не видит сломанных блоков; минус лишние запросы и ошибки в консоли на

- **Сложность:** 3–5 ч на флаг и условия. Риск низкий; решение «что делать с комментариями» —
  продуктовое.

### H3. Любой `#якорь` в адресе уводит на `/movie/<якорь>`; `kp_id` не валидируется — Баг (вживую)

- **Где:** `src/helpers/hashHandler.js:16-19`, `src/router/index.js:53-55`, `src/router/routes.js:19`.
- **Проблема:** `https://reyhoho.fun/top#section-test` перенаправило на
  `/movie/section-test/movie-section-test` с «Произошла неизвестная ошибка. Ошибка: 400»; при этом
  смонтировался плеер и ушли запросы плееров для несуществующего ID. Обычные якоря (включая
  существующий `id="movie-comments"`) использовать невозможно.
- **Причина:** совместимость со старыми ссылками `/#301` реализована веткой `else` для любого хэша;
  параметр маршрута принимает произвольную строку.
- **Решение:**

  ```js
  // hashHandler.js — вместо финального else
  const legacyId = /^#(\d{1,12})$/.exec(to.hash)
  return legacyId ? { path: getMovieSeoPath({ kp_id: legacyId[1] }) } : true
  ```

  ```js
  // routes.js
  path: '/movie/:kp_id(\\d{1,12}|shiki\\d{1,12})/:slug?'
  ```

  Нечисловой ID тогда попадает в `NotFound` без сетевых запросов.
- **Эффект:** работают якоря, исчезают ложные страницы ошибок и запросы с мусорными ID.
- **Сложность:** ~1 ч + тесты роутера. Риск: проверить, что ссылки вида `/movie/shiki123` всё ещё нужны.

### H4. Прямые ссылки на большинство фильмов отдаются с HTTP 404 — Баг (вживую)

- **Где:** хостинг GitHub Pages + `public/404.html`, `index.html:86-105`.
- **Проблема:** `GET /movie/301/` → **404** → JS-редирект на `/?p=…` → загружается prerender главной
  (с её чанками `MovieSearch`, `MovieList` и CSS) → клиентский переход на фильм. Пререндер есть только
  для 298 фильмов из `movies.json`; все остальные страницы поисковик видит как 404, а пользователь
  получает лишний полный цикл загрузки и несовпадение гидрации (HTML главной под маршрут фильма).
- **Причина:** ограничение GitHub Pages — SPA-fallback возможен только через `404.html`.
- **Решение:** сайт уже за Cloudflare — перенести статику на Cloudflare Pages / Workers Static Assets
  с `not_found_handling: "single-page-application"` (fallback отдаётся с кодом 200), а для fallback
  собирать отдельный пустой `shell.html` вместо prerender главной. Минимальный вариант без переезда:
  генерировать нейтральный shell для `?p=`-восстановления.
- **Эффект:** индексируемость всех страниц фильмов, на один сетевой круг и ~62 kB (без сжатия)
  лишнего JS/CSS главной меньше при входе по прямой ссылке, нет мигания главной.
- **Сложность:** 0.5–1 день с проверкой кэша, `CNAME`, service worker и `scripts/browser-artifact-check.js`.
  Риск средний: смена хостинга; откат — вернуть DNS.

### M3. Загрузка плееров не отменяется и не защищена от гонки — Баг (по коду)

- **Где:** `src/composables/usePlayerSources.js:117-165`, `src/components/PlayerComponent.vue:1006-1031, 1056-1066`.
- **Проблема:** `fetchPlayers` не передаёт `signal` и не проверяет актуальность ответа. При уходе со
  страницы цепочка (до 45 с сетевой работы) продолжается; при смене источника в настройках два
  параллельных вызова завершаются в произвольном порядке — побеждает последний ответивший.
  Дополнительно `PlayerComponent` держит собственный `kp_id` из `route.params` параллельно с `props.kpId`.
- **Решение:** `AbortController` на вызов, отмена в `onBeforeUnmount` и перед новым вызовом, счётчик
  поколения перед `applyPlayersData`; `signal` уже поддержан в `getPlayers`. Убрать локальный `kp_id`.
- **Эффект:** нет лишних запросов и устаревших списков плееров.
- **Сложность:** 1–2 ч. Риск низкий.

### M4. История и списки: двойное хранение и полная перезапись `localStorage` на каждое действие — Баг/производительность (по коду)

- **Где:** `src/store/main/main.js:31-106`, `src/utils/localUserLists.js:14-73`,
  `src/components/CardMovie/CardMovie.vue:104-114`, `src/api/user.js:117, 121`.
- **Проблема:**
  1. История лежит и в persisted-store `main`, и в зеркале `reyohoho-user-lists[:owner]`; каждое
     изменение сериализует оба хранилища целиком (в зеркале — `JSON.parse` и `JSON.stringify` всех шести списков).
  2. `CardMovie.loadRatings` на **каждую** карточку без рейтинга вызывает `mainStore.setHistory(history.map(…))`
     — O(N) на карточку, O(N²) на список; при импортированной истории в сотни записей это заметные
     подвисания при прокрутке.
  3. `addLocalListItem(type, id, metadata)` получает полный объект фильма (актёры, `raw_data`, ~10–20 kB)
     вместо карточки; ошибка записи при переполнении квоты проглатывается (`writeLists` → `false`).
  4. `cleanOldHistory` нигде не вызывается; у гостя история не ограничена, а `normalizeHistory(…, 5000)`
     в `AuthSuccess.vue` бросает исключение при превышении — вход завершится ошибкой.
  5. Списки рендерятся целиком (облачная история — до 5000 карточек, списки — до 1000), без виртуализации.
- **Решение:** один источник правды для истории (убрать `history` из `pick` persisted-store либо
  не зеркалировать её); в зеркало писать `normalizeHistory([item])[0]`; исправления рейтингов
  накапливать и применять одним `setHistory` на кадр/батч; ограничить историю гостя
  (`MAX_HISTORY_ITEMS`), удалить мёртвый `cleanOldHistory`; показывать первые 60–100 карточек и
  догружать по `IntersectionObserver` (механизм уже есть на главной).
- **Эффект:** меньше блокировок главного потока при открытии фильма и прокрутке истории, меньше риск
  упереться в квоту `localStorage`.
- **Сложность:** 1–1.5 дня; нужна миграция persisted-данных и обновление `main.persist.spec.js`.
  Риск средний: потеря локальной истории при ошибке миграции — делать с резервной копией ключа.

### M5. Квота облачной истории считает удалённые записи навсегда — Риск

- **Где:** `workers/kinobox-search/migrations/0001_history.sql:11-30`, `history.mjs:137-145`.
- **Проблема:** удаление — это `UPDATE … deleted = 1`, строки не удаляются, триггер
  `history_count_delete` не срабатывает. После 5000 разных фильмов за всё время (включая очищенные)
  новые просмотры получают `409 History capacity reached`, и освободить место нельзя.
- **Решение:** добавить `deleted_at INTEGER`, в `scheduled()` удалять tombstone старше 90 дней пачками
  (триггер сам уменьшит счётчик); либо не считать tombstone в квоте.
- **Эффект:** квота отражает реальный размер истории.
- **Сложность:** 2–3 ч + миграция D1. Риск: tombstone нужны, чтобы импорт не воскрешал удалённое —
  срок хранения выбрать с запасом.

### M6. Импорт списков: по запросу на элемент при лимите 180 запросов/мин — Риск

- **Где:** `src/components/UserLists.vue:327-345`, `workers/kinobox-search/wrangler.jsonc:50-56`,
  `src/api/listMetadata.js`.
- **Проблема:** `importServerLists` шлёт `PUT /list/:type/:id` последовательно без пауз; затем
  дозагрузка метаданных шлёт ещё по `PATCH` на карточку. При быстром соединении и списке в сотни
  элементов лимитер вернёт 429; ошибки только считаются (`failedCount`), повтора и учёта `Retry-After` нет.
  ID импортируются без метаданных, поэтому карточки какое-то время пустые.
- **Решение:** endpoint `POST /api/list/:type/import` по образцу `/api/history/import` (пачки до 40,
  `db.batch`); на клиенте — пауза и повтор при 429.
- **Эффект:** импорт 1000 элементов за ~25 запросов вместо 1000+, без частичных потерь.
- **Сложность:** 4–6 ч (Worker + клиент + тесты). Риск низкий.

### M7. Необъявленная зависимость `lodash.debounce` — Баг (по `yarn.lock`)

- **Где:** `src/components/MovieSearch.vue:174`, `ModalSearch.vue:97`, `ImagePicker.vue:64`; в
  `package.json` пакета нет.
- **Причина:** пакет попадает в `node_modules` только транзитивно через
  `@babel/helper-define-polyfill-provider` (цепочка `workbox-build`).
- **Решение:** `yarn add lodash.debounce` либо собственная функция на 10 строк.
- **Эффект:** сборка не сломается при обновлении PWA-инструментов.
- **Сложность:** 5 минут.

### M8. Тесты падают на актуальном Node — Баг (воспроизведено)

- **Где:** `package.json` (нет `engines`), нет `.nvmrc`, `vitest.config.js`.
- **Проблема:** на Node 26.13 — 52 падения в 11 файлах (`window.localStorage` undefined из-за встроенного
  Web Storage); CI на Node 22 зелёный, локальный запуск — красный.
- **Решение:** `"test:unit": "cross-env NODE_OPTIONS=--no-experimental-webstorage vitest"`
  (`cross-env` уже в devDependencies; с этим флагом на Node 26 проходит 651/651), добавить `.nvmrc` и
  `"engines": { "node": ">=22.4" }`.
- **Эффект:** одинаковый результат локально и в CI.
- **Сложность:** 15 минут. Проверить, что Node 22 в CI принимает флаг.

### M9. Сообщения об ошибках вводят в заблуждение — Баг (по коду)

- **Где:** `src/constants.js:22-64` (`handleApiError`), `src/components/ErrorMessage.vue:25`,
  `src/api/cloudHistory.js:35`, `src/api/workerAccount.js:32`.
- **Проблема:** любой 403 → «недоступно по требованию правообладателя» (Worker отвечает 403 и на
  чужой Origin); 429 и 503 с `Retry-After` → «неизвестная ошибка»; кнопка «Статус» ведёт на
  `http://38.180.83.227:8080/…` — голый IP по HTTP; `response.json()` вызывается до проверки
  `response.ok`, поэтому HTML-ответ 502/504 от Cloudflare даёт `SyntaxError` вместо «сервис недоступен».
- **Решение:** отдельные тексты для 429 («слишком много запросов, повторите через N с») и 502–504;
  403 «правообладатель» — только при явном признаке в теле ответа; `await response.json().catch(() => null)`;
  ссылку статуса вынести в env или убрать.
- **Сложность:** 1–2 ч.

### M10. Плеерный `iframe` без `sandbox`/`referrerpolicy` — Риск (перенос из прошлого аудита)

- **Где:** `src/components/PlayerComponent.vue:36-52`; `src/utils/playerSecurity.js` только считает телеметрию.
- **Проблема:** сторонний код плеера может менять `top.location`, открывать всплывающие окна.
- **Решение:** поэтапно, начиная с
  `sandbox="allow-scripts allow-same-origin allow-forms allow-presentation allow-popups"` (без
  `allow-top-navigation`) для непроверенных origin; `allow="fullscreen; picture-in-picture; encrypted-media"`.
  Матрицу совместимости собирать по уже имеющемуся событию `player_iframe_security`.
- **Сложность:** 1–2 дня из-за ручной проверки каждого плеера. Риск высокий: часть плееров определяет sandbox.

### M11. Комментарии — Баг/UX (актуально, когда backend подключён)

- **Где:** `src/components/Comments.vue:8-9, 264, 300-333, 554-595, 600`.
- «Комментариев пока нет» показывается до загрузки и при ошибке (вживую);
- после любой оценки/правки/удаления перезагружается всё дерево (`loadComments()`), ответ без пагинации;
- `buildCommentTree` — O(n²) (фильтр по всему массиву на каждый узел);
- `currentUser = ref(authStore.user)` — снимок, не реагирует на вход/выход;
- Enter отправляет комментарий — на мобильной клавиатуре нельзя перенести строку.
- **Решение:** счётчик показывать только после успешной загрузки; локальное обновление изменённого
  комментария; индекс `Map(parent_id → children)`; `computed(() => authStore.user)`; на мобильных
  отправка только кнопкой.
- **Сложность:** 4–6 ч.

### M12. Доступность — Баг (частично вживую)

- ~22 обработчика `@click` на `div/span/i` при трёх с клавиатурной альтернативой (например,
  `.spoiler-warning` в `Comments.vue:3`);
- `role="dialog"`/`aria-modal` только в `BaseModal` и `Login`; остальные модальные окна без роли и
  удержания фокуса;
- 8 нативных `confirm()`/`alert()` вместо `BaseModal`;
- `prefers-reduced-motion` учтён в двух местах при анимированных фонах (`LavaLampBackground`:
  `blur(40px)` + бесконечная анимация) и мигающем `text-red-blink`;
- на мобильном кнопки шапки 50×32 и 38×37 px (рекомендуется ≥ 44×44);
- Ctrl+F по умолчанию перехватывается под поиск по сайту (`App.vue:57`), используется устаревший `keyCode`.
- **Решение:** `<button>` вместо кликабельных `div`; общий модальный примитив на базе `BaseModal`;
  глобальное правило `@media (prefers-reduced-motion: reduce)`; для поиска — клавиша `/`, Ctrl+F
  оставить браузеру (или выключить по умолчанию).
- **Сложность:** 1–2 дня. Риск низкий.

### M13. Legacy-backend: открытые пункты прошлого аудита — Риск

Проверено, что всё ещё в коде: `ssl=False` (`backend/kinoserver.py:1525, 1641`); два воркера при
process-local кэше и лимитере (`backend/Dockerfile`); неограниченный рост `ViewEvent`
(`routes_external.py:45`); диапазоны версий без lock (`requirements.txt`); dev-секреты по умолчанию в
`docker-compose.yml`. Новое: лимитер использует `request.ip` (`routes_core.py:216, 240`), а
`PROXIES_COUNT`/`REAL_IP_HEADER` не заданы — за reverse-proxy все клиенты делят один IP и лимит входа
10/мин становится общим. Нет конфигурации ruff — результат линта зависит от версии. Приоритет зависит
от решения по H2: если backend не возвращается в продакшен, эти пункты закрываются его удалением.

### M14. Зависимости — Риск

3 high — `follow-redirects` через `axios` (исполняется только в Node, в браузерный бандл не попадает);
остальное — инструменты сборки (`workbox-build`). `vite-plugin-pwa` и `workbox-build` лежат в
`dependencies`, хотя нужны только при сборке. Решение: обновить `axios`/добавить `resolutions`,
перенести PWA-пакеты в `devDependencies`. 30 минут + полный прогон.

## 5. Идеи улучшений

Отсортированы по отношению эффекта к затратам.

1. **«Повторить» везде, где есть ошибка или пустой результат** (плеер, карточка фильма, поиск,
   случайный фильм). Компонент `ErrorMessage` уже умеет `show-retry`. ~2 ч.
2. **Главная: «Продолжить просмотр» + «Популярное» одновременно.** Сейчас топ виден только при пустой
   истории — вернувшийся пользователь не видит новинок. Показывать 6–12 последних из истории и топ ниже. ~3 ч.
3. **Добавление в списки прямо с карточки** (меню по долгому нажатию/кнопке): сейчас нужно открыть
   фильм. Экономит переход и ожидание плеера. ~4–6 ч.
4. **Память о выбранном плеере по фильму/сериалу**, а не только глобально — возврат к сериалу сразу в
   тот же источник. Store `player` уже хранит похожую карту для KinoBD. ~2 ч.
5. **Подсказки и недавние запросы в поиске** (локально, 5–10 последних) — меньше ввода на мобильном. ~3 ч.
6. **Скрыть «Локальный сервер» и выбор backend в «Расширенные»** — обычному пользователю достаточно
   выбора источника плееров. ~1 ч.
7. **«Случайный фильм» с фильтрами** (жанр/год) — сейчас выбор только из топ-250. Требует нового
   запроса в Worker. ~1 день.
8. **Заголовки безопасности через Cloudflare** (CSP в режиме report-only, `Referrer-Policy`,
   `X-Content-Type-Options`): сейчас главная отдаёт только `Cache-Control`. ~2 ч + наблюдение.

## 7. План по шагам

**Шаг 1 — за один день, без архитектурных решений.** H1, H3, M7, M8, M1, L1–L6, L9. Все правки
локальные, каждая с тестом; отдельные коммиты `fix(...)`.

**Шаг 2 — главный пользовательский сценарий.** C1 вместе с M3 (отмена запросов) и кнопками «Повторить»
(идея 1). Перед выкладкой прогнать `movies.player-fallback.spec.js`, `browser-smoke-check.js` и вручную
открыть 3–5 фильмов с намеренно заблокированным провайдером.

**Шаг 3 — решение по backend (H2).** Выбрать: вернуть backend в прод, перенести функции в Worker или
удалить. До решения — флаг `legacyBackendAvailable` и скрытие блоков (3–5 ч). От выбора зависят M11, M13, L15.

**Шаг 4 — данные и SEO.** M2 (новый источник SEO-каталога), затем H4 (переезд статики на Cloudflare
с fallback 200). После переезда проверить `scripts/browser-artifact-check.js` и индексацию страницы
вне каталога.

**Шаг 5 — хранилище и аккаунт.** M4 (единое хранение истории с миграцией), M6 (пакетный импорт), M5
(очистка tombstone), M9 (тексты ошибок).

**Шаг 6 — качество и долг.** M12 (доступность), M10 (sandbox по матрице плееров), M14, L10–L15,
декомпозиция `MovieInfo.vue` по существующим тестовым границам, обновление `PROJECT_MAP.md`.
